## 为什么需要 RAG 评估
RAG 系统由文档处理、检索、重排序、Context 构建和 LLM 生成多个环节组成。最终答案错误时，原因可能是：

1. 知识库没有正确内容。
2. 文档切分破坏了语义。
3. Retriever 没有召回正确 chunk。
4. Reranker 排序不合理。
5. Context 中存在噪声或冲突。
6. LLM 没有正确使用已检索到的资料。

只看最终答案分数，无法定位具体问题。评估的作用是量化效果、发现瓶颈，并验证模型、Prompt、切分和检索参数的调整是否真的有效。

## RAG 评估的基本层次
RAG 评估通常分为三层：

```text
检索层：找没找到正确资料？
   ↓
上下文层：提供的资料是否相关、完整、无噪声？
   ↓
生成层：答案是否正确、有依据、真正回答了问题？
```

### 1. Retriever 评估
评估候选结果是否包含相关文档，重点关注 Recall、Precision、MRR、NDCG 等指标。

### 2. Context 评估
评估传给 LLM 的上下文是否足够相关、是否缺少关键事实、是否存在大量重复内容。

### 3. Generator 评估
评估最终答案的事实正确性、相关性、完整性、表达质量和引用准确性。

## 评估数据集如何设计
一个基础测试集至少应包含：

```json
{
  "question": "系统支持哪些登录方式？",
  "ground_truth": "系统支持密码登录、短信登录和单点登录。",
  "relevant_doc_ids": ["doc_login_001"],
  "category": "事实问答",
  "difficulty": "easy"
}
```

建议覆盖不同问题类型：
1. 事实型问题：答案通常在单个 chunk 中。
2. 多跳问题：需要组合多个 chunk 的信息。
3. 比较型问题：需要比较不同对象的属性。
4. 总结型问题：需要理解较长上下文。
5. 精确匹配问题：包含产品名、编号、错误码或 API 名称。
6. 无答案问题：知识库中没有足够资料，应当拒答。
7. 冲突问题：不同版本或来源包含不一致信息。

测试集应尽量来自真实用户问题，并划分为开发集、验证集和最终测试集，避免只针对少数示例调 Prompt。

## 检索阶段指标
### Precision@K
Precision@K 表示前 K 个检索结果中相关结果的比例：

$$
\mathrm{Precision@K}=\frac{\text{前 K 个结果中的相关文档数}}{K}
$$

它衡量结果是否“足够干净”。

### Recall@K
Recall@K 表示所有相关文档中，有多少出现在前 K 个结果里：

$$
\mathrm{Recall@K}=\frac{\text{前 K 个结果中的相关文档数}}{\text{相关文档总数}}
$$

RAG 中 Recall@K 很重要，因为正确资料没有被召回时，后续 Reranker 和 LLM 都无法补救。

### F1@K
Precision 和 Recall 可以通过调和平均合并：

$$
F1=2\times\frac{Precision\times Recall}{Precision+Recall}
$$

当 Precision 或 Recall 为 0 时，F1 为 0。

### MRR
MRR（Mean Reciprocal Rank，平均倒数排名）关注第一个正确结果出现的位置：

$$
\mathrm{MRR}=\frac{1}{|Q|}\sum_{i=1}^{|Q|}\frac{1}{\mathrm{rank}_i}
$$

如果正确结果排在第 1 位，倒数排名是 1；排在第 5 位，倒数排名是 $1/5$。

### NDCG@K
NDCG 能处理“相关性有等级”的情况，例如高度相关、部分相关和不相关：

$$
\mathrm{DCG@K}=\sum_{i=1}^{K}\frac{2^{rel_i}-1}{\log_2(i+1)}
$$

$$
\mathrm{NDCG@K}=\frac{\mathrm{DCG@K}}{\mathrm{IDCG@K}}
$$

其中 $rel_i$ 是第 $i$ 个结果的相关性等级，IDCG 是理想排序下的 DCG。

### Hit Rate@K
只关心前 K 个结果中是否至少命中一个相关文档：

$$
\mathrm{HitRate@K}=\frac{\text{命中至少一个相关文档的问题数}}{\text{问题总数}}
$$

对于每个问题只有一个主要参考 chunk 的场景，Hit Rate 很直观。

## 生成阶段指标
### Faithfulness（忠实性）
回答中的关键事实是否能被 Context 支持。高忠实性意味着模型没有凭空添加资料中不存在的内容。

### Answer Relevance（答案相关性）
回答是否真正回应了用户问题，而不是只复述无关 Context。

### Answer Correctness（答案正确性）
回答是否与标准答案或真实事实一致，通常需要结合人工标注或评审模型判断。

### Completeness（完整性）
回答是否覆盖问题所需的关键点，尤其适合多条件、多步骤和比较型问题。

### Citation Accuracy（引用准确性）
引用的来源是否真的支持对应结论。引用存在不代表引用正确，需要检查“结论-证据”是否匹配。

### 风格与格式
根据业务要求评估回答是否符合语言、长度、Markdown、JSON、表格或固定字段格式。

## 端到端评估
端到端评估把用户问题直接输入完整 Pipeline，整体考察：

```text
问题 → 检索 → 重排 → Context → Prompt → LLM → 答案
```

推荐同时记录以下结果：
1. 检索结果和排名。
2. 最终 Context。
3. Prompt 版本。
4. 模型回答。
5. 引用来源。
6. 延迟、Token 数和调用成本。

这样才能把“答案错误”拆解成检索错误、上下文错误或生成错误。

## 人工评估
人工评估适合建立高质量基准和检查自动评估难以识别的问题。

### 推荐评分维度
可以使用 0 到 2 分：

| 维度 | 0 分 | 1 分 | 2 分 |
| --- | --- | --- | --- |
| 正确性 | 错误 | 部分正确 | 完全正确 |
| 相关性 | 没有回答问题 | 部分回答 | 直接回答 |
| 完整性 | 缺少关键点 | 基本覆盖 | 覆盖完整 |
| 忠实性 | 明显编造 | 有少量 unsupported 内容 | 全部有依据 |
| 引用质量 | 无引用或错误 | 部分对应 | 准确支持结论 |

评审指南必须明确说明什么是“相关”、什么是“有依据”，否则不同评审者的结果难以比较。

### 人工评估注意点
1. 随机打乱不同版本答案，减少先入为主。
2. 尽量让评审者同时看到问题、Context、答案和标准答案。
3. 使用两名或以上评审者，计算一致性。
4. 记录分歧案例，用于完善评审标准。

## 自动评估与 LLM-as-a-Judge
### 传统自动指标
对于有标准答案的任务，可以使用 Exact Match、F1、ROUGE 等指标。但开放式 RAG 答案可能有多种正确表达，词面指标不能单独代表事实正确性。

### LLM-as-a-Judge
让另一个 LLM 根据明确评分标准判断回答质量，适合评估忠实性、相关性、完整性和引用质量。

评审 Prompt 应提供：
1. 用户问题。
2. 参考 Context。
3. 系统回答。
4. 评分标准。
5. 固定的 JSON 输出格式。

示例：

```text
请判断回答是否完全由参考资料支持。
只输出 JSON：
{
  "faithfulness": 0,
  "unsupported_claims": [],
  "reason": ""
}
评分：0=不支持，1=部分支持，2=完全支持。
```

LLM-as-a-Judge 也可能产生偏差，因此应使用人工样本校准，不能把评审模型的结果视为绝对真值。

## Ragas：专门用于 LLM 应用评估的开源项目
### Ragas 是什么
Ragas 是 GitHub 上的一个开源 Python 项目，主要用于评估和优化 LLM 应用，尤其适合 RAG（Retrieval-Augmented Generation）系统。

项目地址：[Ragas GitHub](https://github.com/vibrantlabsai/ragas)

可以把 Ragas 理解为“面向 LLM 应用的评估工具箱”，而不是一个向量数据库、Embedding 模型或 RAG 框架。它通常接收 RAG 系统产生的问题、参考上下文、答案和标准答案，然后计算一组评估指标。

### Ragas 能做什么
Ragas 的常见能力包括：

1. 评估 RAG 检索和生成质量。
2. 使用 LLM-as-a-Judge 判断答案的忠实性和相关性。
3. 使用传统指标评估答案，例如字符串匹配或文本相似度。
4. 生成测试数据，覆盖事实问答、多跳问题和不同难度场景。
5. 与 LangChain、LlamaIndex 等 LLM 应用生态集成。
6. 根据生产数据建立反馈和持续评估流程。

因此，Ragas 不只是“一个分数函数”，而是可以用于构建 RAG 评估工作流的项目。

### Ragas 评估一条样本需要什么
一条典型 RAG 评估样本通常包含：

```python
{
	"user_input": "系统支持哪些登录方式？",
	"retrieved_contexts": [
		"系统支持密码登录、短信登录和单点登录。",
		"连续五次密码错误后，账户会暂时锁定。"
	],
	"response": "系统支持密码登录、短信登录和单点登录。",
	"reference": "系统支持密码登录、短信登录和单点登录。"
}
```

字段含义：
1. `user_input`：用户原始问题。
2. `retrieved_contexts`：Retriever 最终返回给生成阶段的上下文片段。
3. `response`：RAG 系统生成的答案。
4. `reference`：人工准备的标准答案，可用于需要参考答案的指标。

如果评估重点是检索质量，还应维护相关文档或相关 chunk 的 ID，便于计算 Recall@K、MRR 等传统指标。

### Ragas 中常见的评估指标
不同 Ragas 版本的指标名称和导入方式可能会变化，使用前应以当前官方文档为准。常见指标概念包括：

#### Faithfulness（忠实性）
判断答案中的事实是否能够被检索到的 Context 支持。

直观计算思路是：

$$
\mathrm{Faithfulness}=\frac{\text{被 Context 支持的事实声明数}}{\text{答案中的事实声明总数}}
$$

例如答案包含 4 个事实，其中 3 个能在 Context 中找到依据，则忠实性约为 $3/4=0.75$。

#### Answer Relevance（答案相关性）
判断答案是否真正回应了用户问题，而不是只重复上下文或输出无关内容。

#### Context Precision（上下文精确率）
判断排在前面的 Context 是否相关，重点关注相关片段是否被放在较高位置，以及无关片段是否过多。

#### Context Recall（上下文召回率）
判断回答所需的关键信息是否已经出现在检索 Context 中。它可以帮助区分“检索没找到”和“模型生成错误”。

#### Answer Correctness（答案正确性）
综合比较生成答案与标准答案之间的事实一致性和语义一致性。

### Ragas 的典型评估流程
```text
准备测试问题
	  ↓
运行 RAG Pipeline
	  ↓
保存问题、Context、答案和标准答案
	  ↓
配置评估 LLM 与 Embedding
	  ↓
运行 Ragas 指标
	  ↓
查看结果并定位瓶颈
```

注意：Ragas 评估本身通常还需要调用一个 LLM 作为评审模型，因此会产生额外的 API 成本和延迟。

### Ragas 基础代码示例
Ragas 的 API 会随版本演进，下面示例展示核心使用思路。具体指标类、数据集类和参数名称应以当前版本文档为准：

```python
from datasets import Dataset
from ragas import evaluate
from ragas.metrics import (
	answer_relevancy,
	context_precision,
	context_recall,
	faithfulness,
)

data = {
	"question": ["系统支持哪些登录方式？"],
	"contexts": [[
		"系统支持密码登录、短信登录和单点登录。",
		"连续五次密码错误后，账户会暂时锁定。",
	]],
	"answer": ["系统支持密码登录、短信登录和单点登录。"],
	"ground_truth": ["系统支持密码登录、短信登录和单点登录。"],
}

dataset = Dataset.from_dict(data)

result = evaluate(
	dataset=dataset,
	metrics=[
		faithfulness,
		answer_relevancy,
		context_precision,
		context_recall,
	],
)

print(result)
```

说明：
1. 某些版本使用 `user_input`、`retrieved_contexts`、`response` 和 `reference` 字段，而旧版本示例可能使用 `question`、`contexts`、`answer` 和 `ground_truth`。
2. 指标可能以对象、工厂函数或不同模块路径提供。
3. 运行代码前，应先锁定 Ragas 版本，并按照该版本的官方文档调整字段名和导入路径。

### 使用 Ragas 结果定位问题
可以用指标组合判断问题所在：

| 现象 | 可能原因 |
| --- | --- |
| Context Recall 低 | Retriever 没有召回关键资料，或知识库缺少内容 |
| Context Precision 低 | 召回噪声多，Top-K 太大或排序质量差 |
| Context 指标高但 Faithfulness 低 | LLM 没有遵循 Context，Prompt 或模型存在问题 |
| Faithfulness 高但 Answer Relevance 低 | 答案有依据，但没有真正回答问题 |
| 检索指标高但 Correctness 低 | Context 正确，但生成、理解或答案组织有问题 |

不要只看 Ragas 的总平均分，应按问题类型、难度、文档来源和模型版本分组分析。

### Ragas 的优点与局限
#### 优点
1. 面向 RAG 和 LLM 应用提供了较完整的评估指标。
2. 可以减少纯人工评估的时间成本。
3. 适合对 Prompt、Embedding、Chunking 和 Retriever 做回归对比。
4. 支持测试集生成和持续评估思路。

#### 局限
1. LLM 评审不是绝对客观，可能受到评审模型能力和 Prompt 的影响。
2. 评估结果依赖 Context、标准答案和字段准备是否正确。
3. 运行指标通常需要调用 LLM，会产生成本。
4. 不同版本 API 变化较快，需要锁定版本并查看对应文档。
5. 对专业领域、中文、代码和表格内容，必须使用真实样本人工校准。

### Ragas 在项目中的推荐使用方式
1. 先准备 50 到 200 条真实或高质量人工构造的问题。
2. 保存每次运行的 query、retrieved contexts、answer 和 reference。
3. 用 Ragas 做快速批量评估，用人工评估校准指标可信度。
4. 分别观察 Context Precision、Context Recall、Faithfulness 和 Answer Relevance。
5. 修改 Chunking、Retriever 或 Prompt 后运行同一测试集进行回归。
6. 记录 Ragas 版本、评审 LLM、Embedding 模型和实验配置。
7. 对低分样本回到错误分析表，确认是检索问题还是生成问题。

## 错误分析方法
建议为每个失败案例标记主要原因：

1. `knowledge_missing`：知识库缺少答案。
2. `parsing_error`：文档解析或清洗错误。
3. `chunking_error`：关键内容被不合理切分。
4. `retrieval_miss`：相关 chunk 没被召回。
5. `ranking_error`：相关 chunk 被排在后面。
6. `context_noise`：Context 中无关内容过多。
7. `context_conflict`：资料之间存在冲突。
8. `generation_error`：Context 正确但 LLM 回答错误。
9. `citation_error`：答案引用与结论不匹配。
10. `guardrail_error`：无答案时没有正确拒答。

错误分类比单纯看一个总分更有价值，因为每类问题对应不同修复方向。

## 实验设计与版本对比
进行 RAG 优化时，一次最好只改变一个主要变量，例如：

1. chunk_size 或 overlap。
2. embedding 模型。
3. Retriever 类型。
4. Reranker 模型。
5. Prompt 模板。
6. Top-K 或 score threshold。

每次实验应记录：
1. 代码版本和配置版本。
2. 数据集版本。
3. 模型版本。
4. 检索和生成指标。
5. 平均延迟和成本。

不要只比较平均分，还要查看不同问题类型、难度和语言类别的表现，防止整体提升掩盖某类任务退化。

## Python 计算基础检索指标
下面示例假设 `retrieved_ids` 是检索结果，`relevant_ids` 是人工标注的相关文档：

```python
def precision_at_k(retrieved_ids, relevant_ids, k):
	relevant = set(relevant_ids)
	top_k = retrieved_ids[:k]
	if not top_k:
		return 0.0
	return sum(doc_id in relevant for doc_id in top_k) / len(top_k)


def recall_at_k(retrieved_ids, relevant_ids, k):
	relevant = set(relevant_ids)
	if not relevant:
		return 0.0
	top_k = set(retrieved_ids[:k])
	return len(top_k & relevant) / len(relevant)


def reciprocal_rank(retrieved_ids, relevant_ids):
	relevant = set(relevant_ids)
	for rank, doc_id in enumerate(retrieved_ids, start=1):
		if doc_id in relevant:
			return 1.0 / rank
	return 0.0


retrieved = ["doc_3", "doc_1", "doc_8", "doc_5"]
relevant = ["doc_1", "doc_5"]

print("Precision@3:", precision_at_k(retrieved, relevant, 3))
print("Recall@3:", recall_at_k(retrieved, relevant, 3))
print("Reciprocal Rank:", reciprocal_rank(retrieved, relevant))
```

计算整个测试集时，应分别计算每个问题的指标，再求平均，而不是把所有文档 ID 混在一起计算。

## 实践建议
1. 先建立真实问题测试集，再开始调参。
2. 同时评估 Retriever 和 Generator，不要只看最终答案。
3. 至少记录 Recall@K、MRR、答案正确性、忠实性、引用准确性和延迟。
4. 加入无答案问题，测试系统是否会诚实拒答。
5. 加入产品编号、代码、长文档、多跳和冲突信息等困难样本。
6. 自动评估用于快速回归，人工评估用于校准和发现新问题。
7. 保存失败案例和完整 trace，建立可持续更新的评估集。
8. 关注平均表现和最差类别，避免只优化容易问题。

## 本章小结
RAG 评估应遵循“分层、可定位、可复现”的原则：

```text
检索：有没有找到正确资料？
Context：提供的资料是否相关、完整、可信？
生成：答案是否正确、有依据、回答了问题？
系统：速度、成本、稳定性和安全性是否达标？
```

只有把各阶段指标和端到端结果结合起来，才能知道 RAG 系统哪里出了问题，以及下一步应该优化什么。
