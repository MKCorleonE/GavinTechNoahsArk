## 为什么文档处理是 RAG 的第一步
RAG 的效果通常由两部分决定：
1. 能否检索到正确内容。
2. LLM 是否能基于正确内容回答。

而检索质量的上限，往往在文档处理阶段就已经决定了。文档脏、切分乱、结构丢失，会直接导致“检不到”或“检到了但不相关”。

## Document Loader：把多源文档变成统一输入
在真实项目里，知识源格式通常非常杂，比如：

1. PDF
2. Word
3. TXT
4. Markdown
5. HTML
6. Excel
7. 网页

Document Loader 的核心任务，是把这些异构文件转成统一的数据结构，供后续清洗、切分、向量化使用。

常见统一结构不是只保留纯文本，而是保留“内容 + 元数据”，例如：

```json
{
	"id": "doc_001_chunk_01",
	"text": "Python 是一种通用编程语言...",
	"metadata": {
		"source": "python_intro.pdf",
		"page": 3,
		"section": "1.1",
		"author": "team-ai",
		"updated_at": "2026-08-25"
	}
}
```

说明：
1. 可以是 JSON、JSONL、数据库记录或对象结构。
2. 关键不是“必须 JSON”，而是“结构统一且可追溯来源”。

## Text Cleaning：让文本可读、可检索
文档抽取后通常不能直接用，需要先清洗。典型问题包括：

1. PDF 乱码
2. 多余空格
3. 页眉页脚
4. 重复内容
5. 特殊符号

清洗目标是“尽量不改变原意的前提下，提升文本质量”。

常见清洗动作：
1. 统一编码与换行符，修复乱码。
2. 去掉重复页眉页脚、页码、版权声明。
3. 合并断裂句子，规范空格和标点。
4. 去除无意义噪声（如连续装饰符号）。
5. 保留必要结构信息（标题层级、表格标题、章节编号）。

注意：清洗不是“越狠越好”。过度清洗会丢掉重要语义或上下文线索。

## Chunking 总览：为什么必须切分
大模型有上下文窗口限制，检索也需要更细粒度的匹配单元，所以要把长文档切成多个 chunk。

切分的目标是三者平衡：
1. 每块足够短，便于检索与拼接。
2. 每块语义完整，避免信息断裂。
3. 块间有适度重叠，减少边界信息丢失。

## Chunk 还是文本吗？
是的。chunk 在切分阶段仍然是文本，还没有向量化。

示例：

```text
原始文档
			↓
Chunk 1：Python是一种编程语言……
Chunk 2：Python最常用于数据分析……
Chunk 3：Python可以通过……
```

后续只有在 Embedding 阶段，chunk 才会被转换成向量表示。

## Fixed-size Chunk
Fixed-size chunk 指按固定长度切分，比如每 500 或 1000 个字符一块。

优点：
1. 实现简单。
2. 性能稳定，易并行处理。

缺点：
1. 容易在句子中间截断，语义不完整。
2. 对结构化文档不友好。

适用场景：快速基线系统、文档格式较规整的场景。

## Character Splitting
Character splitting 是按字符数切分文本，本质上是 Fixed-size 的一种基础实现。

常见做法：
1. 设定 chunk_size（如 800 字符）。
2. 设定 overlap（如 100 字符）。
3. 按滑动窗口生成切片。

风险：中文和英文混合时，字符长度与真实语义长度可能不一致。

## Recursive Character Splitting
Recursive Character Splitting 的思想是“先按大分隔符切，不行再降级到小分隔符”。

示例分隔顺序：
1. 段落分隔（双换行）
2. 单换行
3. 句号/标点
4. 空格
5. 字符级

优点：
1. 比固定切分更容易保留语义边界。
2. 在复杂文本上通常更稳。

这是很多 RAG 框架的默认策略之一。

## Sentence Splitting
Sentence splitting 按句子边界切分，例如按句号、问号、感叹号或 NLP 句法工具切句。

优点：
1. 每块语义清晰。
2. 对问答类检索友好。

缺点：
1. 长句过长时仍可能超限。
2. 对表格、代码、项目符号列表不一定理想。

## Paragraph Splitting
Paragraph splitting 按段落切分，尽量保持作者原始结构。

优点：
1. 保留上下文完整性较好。
2. 适合教程、说明文、技术文档。

缺点：
1. 段落长度差异大，可能导致召回粒度不稳定。

## Semantic Chunking
Semantic chunking 按“语义变化点”切分，而不是纯长度规则。

常见思路：
1. 先切句。
2. 计算相邻句子的语义相似度。
3. 相似度突变时断开。

优点：
1. chunk 主题更聚焦。
2. 对复杂知识库检索效果常更好。

代价：实现复杂度和预处理成本更高。

## Parent-child Chunk
Parent-child chunk 是一种分层切分策略：
1. Parent chunk：较长，保留大上下文。
2. Child chunk：较短，用于高精度召回。

查询时常用流程：
1. 先检索 child 提升命中率。
2. 再回溯 parent 提供更完整上下文给 LLM。

适合长文档和多跳问答场景。

## Overlap 是什么以及怎么设置
Overlap 是相邻 chunk 之间重复的那部分文本，用于缓解边界截断问题。

例如：
1. chunk_size = 500
2. overlap = 100
3. 下一块会复用上一块末尾 100 字符

经验建议：
1. overlap 太小：关键信息可能被切断。
2. overlap 太大：冗余高、索引膨胀、检索噪声增加。
3. 常见起点可设为 chunk_size 的 10% 到 20%，再按评估结果调优。

## 实战建议：如何选择 Chunk 策略
可以按“先简单、再优化”的路径推进：
1. 第一步：用 Recursive Character Splitting + 合理 overlap 建立基线。
2. 第二步：通过检索评估观察命中率和答案质量。
3. 第三步：对关键业务文档引入语义切分或 parent-child。
4. 第四步：持续调参 chunk_size、overlap、召回条数 Top-K。

结论：没有放之四海皆准的最佳切分，只有“对当前数据集和任务目标最有效”的切分策略。
