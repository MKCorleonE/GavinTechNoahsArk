## 什么是 RAG
RAG（Retrieval-Augmented Generation，检索增强生成）是一种将“外部知识检索”与“语言模型生成”结合起来的方法。

可以把它理解成两步：
1. 先查资料：从知识库中找出和问题最相关的片段。
2. 再作答：把这些片段连同问题一起交给 LLM，由 LLM 基于证据生成答案。

它的核心思想是：让模型在回答前“先看资料”，而不是只依赖参数记忆。

## 为什么需要 RAG
仅靠大模型参数记忆会遇到几个常见问题：
1. 知识有时效性，模型训练后新增的信息它不知道。
2. 企业私有数据不会出现在公开预训练语料里。
3. 纯生成容易“看起来合理但事实错误”（幻觉）。

RAG 的价值在于把“最新、私有、可追溯”的知识动态接入问答流程，让答案更准确、更可控。

## RAG 和普通 LLM 的区别
普通 LLM 的回答主要来自参数中的统计记忆；RAG 的回答来自“参数记忆 + 外部检索证据”。

直观对比：
1. 知识来源：
普通 LLM 依赖训练语料；RAG 可接入企业文档、数据库、Wiki、FAQ。
2. 时效性：
普通 LLM 更新慢；RAG 更新知识库即可生效。
3. 可解释性：
普通 LLM 难以追溯；RAG 可返回引用片段和来源。
4. 幻觉控制：
普通 LLM 更易编造；RAG 在高质量检索下显著降低幻觉概率。

## RAG 和微调 Fine-tuning 的区别
RAG 和 Fine-tuning 不是互斥关系，而是解决不同层面的问题。

1. RAG 主要解决“知识接入”问题：
把外部信息在推理时动态注入，不改模型参数。
2. Fine-tuning 主要解决“行为/风格/任务适配”问题：
通过训练改变模型参数，让模型更像某个专家或更擅长某类任务。

常见取舍：
1. 知识更新频繁、强调可追溯：优先 RAG。
2. 输出格式强约束、特定任务能力不足：考虑 Fine-tuning。
3. 企业级系统常见方案：RAG + 轻量微调结合使用。

## RAG 到底解决什么问题
RAG 本质在解决这三个问题：
1. 知识边界问题：模型“不知道”或“记不准”的内容。
2. 知识更新问题：新文档上线后如何快速可用。
3. 可信回答问题：答案如何有依据、可引用、可审计。

因此，RAG 适合知识密集型场景，如客服问答、企业知识助手、技术文档问答、法规合规检索等。

## RAG 的基本架构
一个典型 RAG 系统通常包含：
1. 文档处理模块：加载、清洗、切分文本。
2. 向量化模块：把文本转为 Embedding 向量。
3. 索引与存储模块：向量数据库或混合索引。
4. Retriever：接收查询并召回候选片段。
5. （可选）Reranker：对候选片段重排序。
6. Prompt 构造器：把问题和上下文拼装成输入。
7. Generator（LLM）：生成最终答案。

## Offline / Online 两个阶段
RAG 一般分为离线构建和在线查询两个阶段。

1. Offline（离线）阶段：
目标是“建好知识索引”。主要流程是文档采集、清洗、切分、向量化、入库。

2. Online（在线）阶段：
目标是“实时回答问题”。主要流程是查询改写、检索召回、重排过滤、上下文构造、LLM 生成。

一个常见判断是：离线阶段决定“能不能找到”，在线阶段决定“答得好不好”。

## Knowledge Base 是什么
Knowledge Base（知识库）是 RAG 的外部知识来源，不仅仅是“文档堆积”，而是“可检索、可维护、可更新”的知识系统。

知识库常见形态包括：
1. 产品文档、技术手册、FAQ。
2. 企业制度、流程规范、合规条款。
3. 工单记录、会议纪要、内部 Wiki。

高质量知识库通常具备：结构清晰、版本可追踪、内容去重、更新机制稳定。

## Context 是什么
Context（上下文）是模型在当前一次回答时可见的信息集合，通常由三部分组成：
1. 用户问题。
2. 系统提示词（角色、规则、格式要求）。
3. 检索到的知识片段。

在 RAG 中，Context 质量直接决定答案质量。即使模型很强，如果上下文噪声高、冲突多、关键信息缺失，答案也会变差。

## Retriever 是什么
Retriever（检索器）负责“找资料”，它是 RAG 的入口质量控制器。

它的职责包括：
1. 将用户问题转换为可检索表达（关键词或向量）。
2. 在索引中召回 Top-K 候选片段。
3. 按相关性初步排序，交给后续模块。

常见检索方式：
1. 稀疏检索（如 BM25）：关键词匹配强。
2. 稠密检索（向量检索）：语义匹配强。
3. 混合检索：结合两者优势，工业界最常见。

## Generator 是什么
Generator（生成器）通常就是 LLM，它负责“基于检索证据组织答案”。

在理想状态下，Generator 不是凭空编答案，而是：
1. 理解问题意图。
2. 消化检索上下文。
3. 在遵循提示约束的前提下生成清晰回答。

实践中通常会给 Generator 增加约束，例如“仅基于提供材料回答”“无法确定时明确说明”，以进一步降低幻觉风险。
