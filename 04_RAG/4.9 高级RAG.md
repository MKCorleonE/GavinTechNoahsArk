## 高级 RAG 是什么
基础 RAG 通常是“问题 → 检索 → Context → LLM”。高级 RAG 在此基础上增加查询改写、多路检索、重排序、上下文压缩、结果验证和动态决策。

高级 RAG 主要解决：
1. 用户问题表达不清，导致检索不到内容。
2. 单一检索方式无法同时处理语义和精确关键词。
3. Context 太长、太杂，模型难以抓住重点。
4. 一次检索不足以回答多跳或复杂问题。
5. 检索结果质量不稳定，需要自我检查和纠错。

## Query Transformation（查询转换）
查询转换是先让模型改写用户问题，再使用改写后的问题检索。

常见方式：
1. Query Rewrite：将口语改写为清晰查询。
2. Query Expansion：增加同义词、相关术语和关键词。
3. Query Decomposition：把复杂问题拆成多个子问题。
4. HyDE：先生成假设性答案，再用假设答案的向量检索真实文档。

查询转换可以提高召回率，但也可能引入模型误解。因此应保留原始问题，并在必要时同时检索原问题和改写问题。

## Multi-Query Retrieval（多查询检索）
多查询检索让 LLM 针对一个问题生成多个不同角度的查询：

```text
原始问题
	↓
查询 1、查询 2、查询 3
	↓
分别检索
	↓
合并、去重、排序
```

例如“如何部署系统”可以拆成安装依赖、环境变量、启动命令和常见错误四个查询。

优点是能覆盖不同表达，缺点是会增加 embedding、检索和后续处理成本。

## RAG-Fusion
RAG-Fusion 是多查询检索的进一步形式：先生成多个查询，再对每一路结果进行排序融合。

常用 RRF（Reciprocal Rank Fusion）：

$$
\mathrm{RRF}(d)=\sum_{i=1}^{m}\frac{1}{k+\mathrm{rank}_i(d)}
$$

它不直接比较不同检索器的原始分数，而是使用排名，因此适合融合向量检索、BM25 和多个改写查询的结果。

注意：查询数量过多会增加噪声，应限制查询数量并对最终结果重新去重和精排。

## Self-Query Retriever
Self-Query Retriever 让 LLM 将自然语言问题拆成两部分：
1. 语义查询文本。
2. metadata 过滤条件。

例如：

```text
问题：查找 2025 年以后发布的 Python 部门安全文档
语义查询：Python 安全文档
过滤条件：year > 2025 AND department = "Python"
```

它适合文档带有时间、作者、部门、产品、权限和类型等结构化 metadata 的场景。

生产环境必须校验 LLM 生成的过滤条件，防止越权访问、非法字段和无法执行的查询。

## Parent-Document Retriever
Parent-Document Retriever 使用“小块检索，大块返回”的策略：
1. Parent：较大文档片段，保留完整上下文。
2. Child：较小检索片段，提高匹配精度。

```text
Parent 文档
	├── Child 1
	├── Child 2
	└── Child 3

检索 Child 2 → 返回对应 Parent
```

它解决了固定小 chunk 上下文不足、固定大 chunk 检索不精确的问题，但需要维护父子 ID 映射，并控制返回 Parent 的总长度。

## Hierarchical Retrieval（层级检索）
层级检索将知识库组织成多个层次：

```text
文档
  ↓
章节
  ↓
段落
  ↓
句子或细粒度 chunk
```

系统可以先检索相关文档和章节，再在候选范围内检索段落或句子。这样既缩小搜索空间，又能保留文档结构。

它适合技术手册、法规、书籍和大型企业知识库。层级越多，检索链路越复杂，因此需要重点监控每一级的召回损失。

## Contextual Compression（上下文压缩）
上下文压缩从召回 chunk 中提取与当前问题直接相关的句子，删除无关内容。

常见方法：
1. Reranker 过滤低相关 chunk。
2. LLM 抽取相关句子。
3. 句子级相似度筛选。
4. 对重复内容去重。
5. 对长段落做问题相关摘要。

目标可以表示为：

$$
	ext{高相关信息密度} = \frac{\text{与问题相关的 Token 数}}{\text{Context 总 Token 数}}
$$

压缩时必须保留否定、条件、时间、例外和数值等限定信息，不能只保留看起来重要的关键词。

## Adaptive Retrieval（自适应检索）
自适应检索根据问题难度动态决定检索策略，而不是所有问题都使用相同流程。

例如：
1. 简单闲聊：不检索，直接回答。
2. 单事实问题：一次向量或关键词检索。
3. 精确编号问题：优先 BM25 或过滤检索。
4. 多跳问题：分解查询并多轮检索。
5. 低质量召回：改写问题后重新检索。

自适应策略可以降低平均延迟和成本，但决策器本身也可能判断错误，需要设置最大检索次数和超时上限。

## Agentic RAG（智能体式 RAG）
Agentic RAG 由 Agent 规划检索步骤，并根据中间结果决定下一步行动。

```text
问题
 ↓
Agent 制定计划
 ↓
调用搜索、数据库或计算工具
 ↓
检查结果是否足够
 ├── 否：继续检索或改写
 └── 是：构建 Context 并回答
```

它适合复杂、多步骤、需要多个工具协同的问题。与固定 Pipeline 相比，它更灵活，但也更难控制成本、循环次数、权限和最终行为。

## Corrective RAG（纠错式 RAG）
Corrective RAG 会在生成前评估检索结果：
1. 判断结果是否与问题相关。
2. 如果质量足够，继续生成。
3. 如果质量不足，改写查询或切换检索源。
4. 必要时调用 Web Search 或其他外部工具。

```text
Retriever
	↓
检索质量评估
	├── 通过 → Reranker → LLM
	└── 不通过 → Query Rewrite / Web Search → LLM
```

纠错机制不能保证答案一定正确，但可以减少“检索结果明显错误却仍然生成答案”的情况。

## Self-RAG
Self-RAG 让模型在生成过程中判断是否需要检索、检索结果是否有用，以及答案是否需要进一步检查。

它通常包含三个判断：
1. 是否需要外部知识。
2. 当前检索内容是否支持回答。
3. 当前生成内容是否忠实、完整。

Self-RAG 更像一种带反思和控制信号的生成策略。实现时需要额外的训练、控制逻辑或评审模型，不等同于在 Prompt 中简单写一句“请自我检查”。

## Graph RAG
Graph RAG 将知识图谱或实体关系图引入检索流程。文档中的实体成为节点，实体之间的关系成为边。

```text
文档 → 实体抽取 → 关系抽取 → 图谱构建
								 ↓
问题 → 实体定位 → 图遍历/社区检索 → Context → LLM
```

它适合：
1. 多跳关系问题。
2. 需要理解实体关联的问题。
3. 企业组织、供应链、产品依赖和科研文献分析。

难点包括实体消歧、关系抽取错误、图谱更新成本和图结构与原文证据的对齐。

## 多模态 RAG
多模态 RAG 不只检索文本，还处理图片、表格、音频和视频。

常见流程：
1. PDF 页面解析为文本、图片和表格。
2. 图片使用视觉模型生成描述或向量。
3. 表格保留结构，同时生成可检索文本表示。
4. 文本和视觉向量分别或统一建立索引。
5. 根据问题检索对应模态内容，并交给多模态 LLM。

适合财务报表、技术图纸、医学影像、产品图片和会议视频等场景。不能把图片简单转换成一段粗略描述后就认为完成了多模态检索，应保留原始资源和准确来源。

## Long-context RAG
Long-context RAG 利用支持超长上下文的模型处理大量文档，但长上下文不等于不需要检索。

主要取舍：
1. 全量输入：上下文完整，但 Token 成本和噪声较高。
2. 检索输入：成本低、重点明确，但可能漏召回。
3. 分层输入：先摘要或定位，再读取局部原文。

还要注意 Lost in the Middle：关键信息放在超长 Context 中间时，模型可能不容易利用。因此应排序、压缩并在必要时重复关键来源。

## 高级 RAG 的综合架构
一个较完整的高级 RAG 可以采用：

```text
用户问题
	↓
问题分类与权限校验
	↓
Query Rewrite / Decomposition / Multi-Query
	↓
Dense Search + BM25 + Metadata Filter
	↓
结果合并（RRF）
	↓
Reranker
	↓
Parent 回溯 / 层级检索 / Context Compression
	↓
Context 质量检查
	├── 不足：纠错、重新检索或外部搜索
	└── 足够：Prompt 构建
	↓
LLM 生成与引用
	↓
答案校验与反馈记录
```

不要一开始就叠加所有高级组件。应根据错误分析结果引入相应能力，否则系统复杂度会超过收益。

## 高级 RAG 的工程实践
### 延迟与成本
1. 对文档 embedding 和索引构建做缓存。
2. 并行执行多查询和多路检索。
3. 限制 Agent 最大步数和最大 Token 数。
4. 对简单问题使用轻量路径。

### 数据与索引
1. 保存文档、chunk、parent-child 和 metadata 的稳定 ID。
2. 记录索引版本、模型版本和处理参数。
3. 支持增量更新、删除和权限变化。
4. 对向量、关键词和图索引进行一致性检查。

### 安全与权限
1. 在检索前执行用户权限过滤。
2. 防止 Self-Query 生成越权条件。
3. 将检索内容视为不受信任数据，防范 Prompt Injection。
4. 对答案和引用执行敏感信息检查。

### 可观测性与评估
记录每次查询的改写结果、检索路径、候选分数、最终 Context、模型版本、Token、延迟和答案。

同时评估 Recall、Context Precision、Faithfulness、Answer Relevance、引用准确性、成本和稳定性。

## 本章代码项目
建议按以下顺序实现高级 RAG Demo：

### 项目一：Multi-Query + RRF
```text
问题 → 生成多个查询 → 多路检索 → RRF → Top-K
```

### 项目二：Parent-Child Retrieval
```text
Parent 文档 → Child 切分 → Child 检索 → Parent 回溯 → Context
```

### 项目三：Adaptive Retrieval
```text
问题分类 → 决定是否检索 → 决定检索次数和 Top-K → 生成答案
```

### 项目四：Corrective RAG
```text
检索 → 质量评估 → 通过则生成；不通过则改写并重新检索
```

一个通用的多路结果融合函数如下：

```python
def reciprocal_rank_fusion(rank_lists, k=60):
	 scores = {}

	 for rank_list in rank_lists:
		  for rank, document_id in enumerate(rank_list, start=1):
				scores[document_id] = scores.get(document_id, 0.0)
				scores[document_id] += 1.0 / (k + rank)

	 return sorted(scores, key=scores.get, reverse=True)


query_results = [
	 ["doc_2", "doc_1", "doc_5"],
	 ["doc_1", "doc_3", "doc_2"],
	 ["doc_4", "doc_2", "doc_1"],
]

print(reciprocal_rank_fusion(query_results))
```

推荐最终对比：基础 RAG、Hybrid Search、RAG-Fusion、加入 Reranker 和加入纠错机制后的 Recall、答案质量、延迟与成本。
