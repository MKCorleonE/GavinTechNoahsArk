# Order Router 缺陷修复题：题目整理与 AI 协作指南

> 说明：本文根据题目截图整理。对具体代码缺陷的判断属于基于投诉现象的推测；正式作答时应以实际代码、测试和运行结果为准。

## 一、题目背景

你刚加入一家中型电商平台，担任后端工程师。前任团队上周离职，系统昨晚收到客户投诉，同时 CI 测试失败。

你负责的服务名为 `order-router`，它是一个 Python 微服务，负责：

- 管理库存预留；
- 管理订单生命周期；
- 向第三方通知微服务发送出站通知。

需要先阅读客户投诉报告：`customer_bug_report.md`。

## 二、任务要求

### 1. 修复代码并使测试通过

运行：

```bash
pytest tests/ -v --tb=short
```

`tests/` 中只有完整测试集的代表性子集。最终还会使用覆盖相同模块、但更广泛的隐藏测试评估。因此不能只针对当前失败用例硬编码，必须找出真实根因并作出通用修复。

允许修改的文件：

```text
app/inventory.py       # 库存预留逻辑
app/notifications.py   # 出站通知调用
app/orders.py          # 订单查询与生命周期辅助逻辑
root_cause_note.md     # 根因说明
```

其余文件均为只读。

### 2. 撰写根因说明

完成 `root_cause_note.md` 中的模板。篇幅控制在 3～5 句话，重点说明每个问题**为何发生**，而不只是描述改了哪些代码。该文档由招聘团队人工审阅，以清晰、准确为目标。

## 三、项目结构

```text
app/
  models.py          SQLAlchemy ORM 模型：Inventory、Order
  database.py        生产环境数据库引擎／会话配置（测试中不使用）
  inventory.py       reserve_stock、release_stock              ← 可修改
  notifications.py   notify_customer                           ← 可修改
  orders.py          get_pending_orders、create_order、fulfill_order  ← 可修改

tests/
  test_inventory.py
  test_notifications.py
  test_orders.py

conftest.py            所有测试共享的 pytest fixture，只读
customer_bug_report.md 客户投诉及其影响说明，只读
migration_notes.md     数据库迁移历史，只读
root_cause_note.md     你的根因分析说明，可修改
```

补充信息：

- 测试使用内存 SQLite 模拟全部数据库 I/O，不需要外部服务。
- `app/database.py` 是生产数据库连接配置；测试使用自己的 SQLite 引擎，通常不需要改它。
- 禁止把仅适用于测试的数据或条件硬编码进应用代码。
- 修复必须能用于生产环境，不能只满足当前测试。

## 四、客户投诉内容

### 问题 1：订单送达后仍显示为 Pending

多个客户反馈：订单面板仍将订单显示为 `Pending`，但商品数周前已经送达。此问题只影响三月平台迁移前下单的客户，近期订单不受影响。

示例：一笔二月的订单在追踪页面显示于 2 月 28 日已送达，但后台仍显示为 `Pending`。

### 问题 2：缺少确认邮件

履约合作方报告：部分客户没有收到送达确认邮件，且问题不稳定、无法稳定复现。受影响订单在通知服务仪表盘上没有任何入站请求记录，但客户也从未离开过服务。

这些订单在应用日志中没有报错。

### 问题 3：闪购期间库存变成负数

最近两次闪购中，多个高需求商品的库存变成负数。例如商品 1 和 42 在促销结束后均显示 `stock = -3`，导致超卖，之后不得不取消每个商品的三笔订单。

促销持续约 60 秒，同时有大约 40～80 个并发结账请求；低流量下不出现此问题。

## 五、从投诉现象推断的可能根因

以下并不是最终答案，必须结合代码、迁移记录和测试验证。

| 现象 | 可能根因 | 应重点检查的位置 |
| --- | --- | --- |
| 旧订单已送达却仍显示 Pending | 迁移前后的订单状态值不兼容；例如旧值为 `delivered`，新代码只识别 `fulfilled`，或待处理订单的筛选未排除旧状态。 | `migration_notes.md`、`app/orders.py`、订单测试 |
| 部分订单未发确认邮件，通知服务无请求且无应用报错 | `notify_customer` 根本没有调用，或调用条件错误；也可能在错误的订单状态分支中被跳过。需要确认通知是否应只在订单成功完成后发送。 | `app/orders.py`、`app/notifications.py`、通知测试 |
| 高并发时库存为负数 | “检查库存”与“扣减库存”不是原子操作。多个请求同时读到同一旧库存后都通过检查并扣减，产生超卖。 | `app/inventory.py`、库存测试、数据库操作方式 |

特别注意：单纯把 `stock > 0` 改为 `stock >= quantity` 可能只修复数量判断，**并不能自动解决并发竞争**。应检查数据库更新是否能保证“库存足够才扣减”这一操作整体执行。

## 六、推荐完成流程

### 第一步：阅读投诉报告与迁移记录

先明确客户实际遇到的现象、预期行为、影响范围和历史兼容性信息。不要看到失败测试就直接修改代码。

### 第二步：运行测试并记录失败

```bash
pytest tests/ -v --tb=short
```

记录每个失败测试：它属于库存、订单还是通知模块；测试期望什么；当前实际结果是什么。

### 第三步：将测试、实现和投诉对应起来

对每一个失败项回答四个问题：

```text
测试期望什么？
当前代码实际上做了什么？
哪个业务规则被遗漏、误解或实现反了？
怎样修复才能覆盖正常路径与边界情况？
```

### 第四步：只修改允许的应用文件

在 `app/inventory.py`、`app/notifications.py`、`app/orders.py` 中做与根因直接相关的最小修改。不要修改测试、模型、数据库配置或 fixture；不要根据固定订单号、商品号、测试字符串等写特殊判断。

### 第五步：循环验证并主动考虑隐藏测试

每次修改后重新运行：

```bash
pytest tests/ -v --tb=short
```

除了现有测试，还要自行检查：

- 库存刚好等于购买数量；
- 库存为零或不足；
- 多个并发预留请求；
- 商品或订单不存在；
- 同一订单重复完成；
- 非法订单状态转换；
- 没有待处理订单；
- 旧迁移数据的状态值；
- 数据库写入失败时，是否已经错误地发送通知。

### 第六步：填写根因说明

根因说明应围绕“根因 → 后果 → 修复原则”。例如：

```text
旧订单的历史状态值没有被待处理订单查询正确识别，导致已送达的迁移订单仍被归类为 Pending。
确认通知的调用被错误的状态分支跳过，因此部分成功送达的订单没有向通知服务发出请求。
库存预留将可用量检查和扣减拆分为独立操作，在并发结账时允许多个请求同时消耗相同库存，造成超卖。
修复后，订单状态兼容历史数据，通知仅基于已成功持久化的履约结果触发，库存扣减遵循原子的“库存足够才更新”原则。
```

实际表述必须基于最终确认的代码根因，不能照抄此示例。

## 七、在允许使用 AI 的考试中如何协作

先确认考试规则明确允许使用 AI，以及允许向 AI 提供题目、代码和测试内容。不要提供账号、密钥、真实客户数据或不属于考试范围的材料。

AI 最适合协助你进行：阅读、对比、提出假设、设计边界测试、审查方案和润色根因说明。你自己应判断它的结论是否确实由代码和测试支持。

推荐提供材料的顺序：

1. 客户投诉报告和题目限制；
2. 完整测试失败输出；
3. 相关测试文件；
4. 对应实现文件；
5. 你的最终 diff 与测试结果。

## 八、可直接复用的 AI 对话模板

### 第一轮：建立上下文，不急于修改

```text
我在做一个 Python 后端缺陷修复题。请只基于我提供的文件分析，不要假设未给出的代码。

题目允许修改：[允许修改的文件]。
题目禁止修改：[只读文件]。

请先阅读客户投诉、测试和相关实现，列出：
1. 每个失败测试的预期；
2. 当前代码行为；
3. 最可能的根因；
4. 可能被隐藏测试覆盖的边界情况。

此时不要修改代码。
```

### 第二轮：深挖单个问题

```text
请聚焦 [库存 / 订单状态 / 通知] 问题。根据以下代码和测试，解释从输入到错误结果的完整执行路径。

请明确区分：
- 代码和测试已经直接证明的结论；
- 仍需要验证的猜测。

然后给出 2～3 种修复思路，并说明各自的生产环境风险。
```

### 第三轮：请求最小、通用的修复

```text
请选择最符合业务语义、不会依赖测试数据的方案。请给出最小代码改动，并逐行说明：
- 为什么能够修复根因；
- 是否会影响正常路径；
- 哪些边界情况仍须测试；
- 是否存在事务、并发或重复调用风险。

不要修改测试文件，不要加入针对固定订单号、商品号或字符串的特殊判断。
```

### 第四轮：让 AI 反驳自己的方案

```text
请作为严格代码审查者反驳你刚才的方案：尝试构造至少 5 个隐藏测试或生产场景，特别包括旧数据兼容、空结果、库存恰好为零、并发请求、重复调用、数据库提交失败。

若方案不可靠，请提出更稳妥的最小替代方案。
```

### 第五轮：提交前审查

```text
以下是最终 diff 和测试结果。请只做审查，不要重写代码：
[粘贴 diff 和 pytest 输出]

请检查：
1. 是否违反题目规定的可修改文件范围；
2. 是否存在仅为测试硬编码的逻辑；
3. 是否遗留并发、事务一致性或重复调用问题；
4. 是否可据此写出一份 3～5 句话的 root_cause_note。

请帮我起草根因说明，重点写问题为什么发生、造成什么后果和修复原则，而不是罗列代码改动。
```

## 九、针对库存并发问题的关键追问

遇到库存问题时，向 AI 额外追问：

```text
这个方案在多个请求同时执行时是否仍然正确？请用“库存为 1、两个请求同时购买 1 件”的时序具体说明每一步会发生什么。

检查库存和扣减库存是否在数据库层面作为一个不可分割的操作完成？如果不是，请说明这种方案为什么仍可能超卖。
```

如果 AI 的建议只修改库存的比较符号，却没有说明并发请求如何避免同时通过库存检查，则该建议通常不够可靠，需要继续审查。
